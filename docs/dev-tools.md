# 对局机器人 / 回放诊断（开发端工具）

> 这些工具**只在 `tools/` 下**，不属于 `dist` / `dist-electron`，因此
> **不会进安装包（baseline）也不会进增量更新清单**，玩家永远下载不到。
> `tools/pack-update.mjs` 里有硬校验：内容树出现 `dist`/`dist-electron` 以外的路径就直接打包失败。

## 用法

```bash
npx tsx tools/fuzz-rules.ts                      # 默认 20 局 × 250 步
npx tsx tools/fuzz-rules.ts --games 8 --steps 300 --seed 1
```

每一步枚举"界面上真的会给出按钮"的动作（依据 `src/ui/Battlefield.tsx` 的判定），随机挑一个执行，检查 7 条不变量：

| 不变量 | 抓什么 |
|---|---|
| 提示可解 | 有提示时至少存在一个能生效的动作（否则整局卡死） |
| 拒绝有反馈 | 动作没生效时必须留下战报文字（"点了没反应"） |
| 卡牌守恒 | 每个玩家的卡牌实例集合前后一致（不增不减不重复） |
| 数字合法 | 费用池 / 计数器不为负 |
| 能推进 | 连续 61 步无动作生效 → 逐个试完所有候选后仍无效才算真卡死 |
| 可复现 | 同种子 + 同流水重放，状态投影一致 |
| 覆盖度 | 统计有多少张卡被成功使用过 |

失败时写出**最小复现流水**（`tools/_fuzz/repro-*.json`，操作流水里的 uid 已归一化成"第几张卡"）。

## 截至目前的发现（v0.21.0，8 局 × 300 步）

| 类别 | 数量 | 判断 |
|---|---|---|
| 静默失败（局末 296~298 步的 移动 / 宣言 / 登场） | 10 | **待复核**：界面会给按钮，但集中在局末，可能是机器人把局面打到退化状态 |
| 不可复现 | 4 | **待定性**：卡序映射下标会随卡牌集合变化而错位，需独立进程回放 + 卡号一致性校验 |
| 卡死 / 卡牌守恒 / 负数 | 0 | 干净（覆盖仅 27/208 张卡，样本仍小） |

## 确认发现 #1：界面「移动」按钮与引擎判定不一致（登场回合限制）

对比 `src/core/rules.ts` 的两个函数：

- `validMoveTargets()`（第 2012 行）—— **界面用它决定「移动」按钮能否点、以及高亮哪些格子**
- `moveCharacter()`（第 2041 行）—— 真正执行移动

两者判定**不一致**，`validMoveTargets` 少了这一条：

```ts
// 只在 moveCharacter 里有：
if (inst.deployedTurn !== null && !eng.hasAggressive(next, uid)) {
  log(next, '登场ターン制限中，无法使用移动类基本能力。');
  return next;
}
```

后果：**刚登场、且没有「アグレッシブ」的角色，界面照样给你「移动」按钮和可点位置，玩家选完位置后引擎拒绝、只有一句战报** —— 属于"点了没反应"同一族（用户感受是"我点了移动，位置也选了，结果什么都没发生"）。

**结论（已由维护者裁定 + 已修）**：错的是**引擎**这一条，不是界面。移动类基本能力**不受**「登场ターン制限」限制（アグレッシブ与否都能宣言）；登场ターン制限只管「攻击」与「[T] 费用支付」。用户指出规则后，已把 `moveCharacter` 里这条多余的判定删除（`rules.ts`，改为注释说明），修复后 `test-rules` 314 / `test-6960` 20 / `test-perms` 19 全绿 —— 说明原有的单元测试**没有覆盖**这条限制，正是机器人把它挖出来的。

## 待做功能：单人测试模式（仅开发版，不进正式打包）

**需求（用户已确认）**
- 主菜单加「🧪 单人测试模式」入口（**只在开发构建里显示**）；
- 进入后**不需要选卡组**，直接进战场；
- 点击**我方卡组位置**弹出**卡牌检索二级界面**（风格同「卡组制作」）：可按**属性**（雪/花/宙/日/月）与**类别**（角色/道具/场地）筛选、可搜索；
- 点一张卡 → **直接加入我方手牌**（便于测单个效果与联动）；
- **范围：只给我方操作**（对手侧暂不支持，用户已确认）；
- 便利按钮（可选）：重置我方场上角色为未行动、抽满手牌。

**为什么不能随便写进 `src/`**：界面产物 `dist/` 本身就是发给玩家的内容，写在 `src/` 里就会跟着发出去。
因此采用**构建期排除**而不是运行期开关：

1. 以构建标志 `VITE_DEV_TOOLS=1` 为条件，用**动态 import**（`await import('./ui/TestMode')`）引入；正式构建时该分支是常量假，Vite 不产出该 chunk；
2. 两个构建命令：`npm run build`（正式，无测试模式）／`npm run build:dev`（开发，含测试模式）；
3. `tools/pack-update.mjs` 加**硬校验**：正式打包时内容里若出现测试模式 chunk，**打包直接失败**（与"`tools/` 不许进内容树"同一道闸）。

**已知边界（需在界面上写明）**：该模式绕过"卡组 60 张 / 同编号最多 4 张 / 卡牌守恒"等校验，属沙盒；
因此它的对局**不能**用于验证张数守恒类不变量，那类仍需正常模式跑。

## 确认发现 #2：静默拒绝的触发局面（机器人实测）

给报告补上"当时手牌/卡组/场上数量"后，10 处静默拒绝的现场是：

```
手牌 0 / 卡组 51 / 全场角色 2
手牌 1 / 卡组 51 / 全场角色 1
```

**卡组还有 51 张**，所以不是"牌打空了"的退化局面。被拒的动作是界面真会给按钮的 `moveCharacter` / `requestDeclare` / `requestPlayCharacter`。**具体走的是哪条 return 分支仍需回放逐帧确认**（读代码看，`moveCharacter` 里大部分拒绝分支都有战报，只有少数是静默的，需要回放定位到底是哪一条）。
